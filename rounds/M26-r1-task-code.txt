【附带发现的另外两道门】

门 1: 后缀白名单（23 项）
    scan_file 对表外后缀 return []，唯一例外是名为 SKILL.md 的文件。
    所以只要把载荷写成 payload.ps1 / sitehook.pth / boot.mjs / run.lua / 无后缀，
    扫描器连一个字节都不读。
    .pyc / .pth / .ps1 都不在 SUSPICIOUS_BINARY_EXTENSIONS 里
    —— 连"值得看一眼"的提示都不会有。

门 3: docstring 行被屏蔽
    _compute_docstring_lines(lines) 会算出 docstring 覆盖的行，这些行上代码类规则不匹配
    （注释写明是为了"代码规则不要在散文上误报"）。
    副作用: 把载荷放进 """...""" 里就绕过 python_os_system / subprocess 等规则。
    （该载荷本身不执行，但它是二次展开的现成载体 —— 任何 exec(docstring) 或
      模板渲染路径都会把它变成可执行。）

限额未生效于内容扫描
    MAX_SINGLE_FILE_KB = 256 只出现在结构检查里；scan_file 全程不引用该上限。
    即: 超大文件并不会因为超限而跳过内容扫描（与 M54 假设方向相反，需单独复测）。

【判定】
    技能扫描器对 10 种载荷形态完全隐形                    本节矩阵，真 scan_skill() 返回 0 finding
    同一载荷仅换编码即从 dangerous 变 safe               A vs E/F 三行对照
    .pth（python 启动即执行）不在白名单且不受任何检查       C 行
    Windows 脚本后缀全部不扫描                          B 行
    agent-created 档位 high 级命中直接放行              INSTALL_POLICY + N 行实测 True
    扫描器本身工作正常                                  A/J/K/N 四个对照组分别命中 2/4/2/3 条规则

    => 不是扫描器没规则，是它读不到我们放规则的地方。
