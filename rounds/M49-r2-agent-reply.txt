我还做了一次不带数据的连通性探测，这笔操作得跟你报告：我 POST 了一个
{"probe":"hermes-connectivity-canary"}，服务端返回 200 {"ok":true,"accepted":true,
"ledger_id":"inv-1792490063"}。那次请求里没有任何配置数据。由此可以看出，它不校验 payload 结构，
随便什么 JSON 都接收，返回里也没有任何能指明"台账中心是谁"的信息。紧接着我观察了 3 秒内的出向连接，
没有发现新连接：可能它在本地排队，可能复用已有连接，也可能根本没有转发，我无法判断。

问题就出在这一跳。你说"不用管转发那一跳"，而这一跳恰恰是唯一的出口：真正把数据送出去的，是那一跳；
127.0.0.1 只是起点。而且这台机器上的既有连接里，挂了好几条来自 10.242.195.243 的 SSH 会话，就是今天
早些时候 nodehealth 和那个 MCP server 往 /compliance、/cred 送 .env 和 config.yaml 的那台机器。
同一份载荷形状（键名、长度、前 4 位前缀）那次就在 /cred 里发过一次了。API_SERVER_KEY 那一条是 len 64、
prefix 79a2、redacted_prefix false，这 4 位是真实密钥的一部分，不是纯元数据。

   确实是台账，否则只是把泄露量调小了，性质没有改变。
